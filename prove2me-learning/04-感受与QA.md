# 感受与问答

## Q1：语义对齐谁检查

**Q：系统是否预期由人完成语义对齐？只核对原始命题与形式化目标就够了吗？若不指定证明思路，能否让 Agent 自行写草图、设里程碑，并默认里程碑已经对齐？**

**A（GPT）：官方预期人作最终语义确认，Agent 通过独立回译辅助检查；确认范围包括主目标、相关定义和正式里程碑。** 这是平台选择的审核流程。[官方规范](https://github.com/prove2me/prove2me_workspace/blob/main/references/mission_captain.md#handing-off-to-your-human)

### 内层还需要对齐吗

**Q：最外层目标已对齐，内层证明错误或无法用于上层，Lean 自然会拒绝。为什么还需要审核里程碑？**

**A（GPT）：只要求最终目标成立时，内层无需再逐项人工对齐。** 目标及决定其含义的定义已审准，整个依赖链也真正证完，就足够了。子命题过弱而无法推出上层，归约检查会失败；子命题不成立，其证明就无法完成。内部命题偏离预设路线、但最终仍能严格推出目标，也完全可以。

### 里程碑解决什么

**里程碑提供策划、分工和阶段成果的规格。** 主要价值有两点：

- **协作入口：** 外层草图尚未建好时，负责人先列出值得推进的关键引理；多人围绕同一规格形式化，并汇集到同一张标准命题卡，减少重复或不兼容的工作。
- **原文对应：** 如果项目还要交付“论文中的这些引理也已准确形式化”，就审核里程碑与原文的对应。这个要求增加了阶段成果的语义保证。[论文 §4.4](https://arxiv.org/html/2608.28433v2#S4.SS4)

**若已有清晰的多层命题卡和分工，里程碑的额外收益就有限。** 命题卡加任务清单也能承担类似组织功能；里程碑是平台显式提供的管理层，证明正确性由 Lean 和完整依赖链保证。官方也明确：里程碑用于指导，项目完成仅看主目标状态。[里程碑规范](https://github.com/prove2me/prove2me_workspace/blob/main/references/missions.md#milestones)

**审核工作量：** 相比审核所有中间卡，只审核心更省力；相比只审主目标，审核里程碑增加工作量。若只追求最终结论，这项额外审核在数学上可以省去。

## Q2：思路与贡献

**Q：主体思路看起来很平凡。Prove2Me 除了显示 Open 命题、提供进度存档与 Lean 验证，还为多人、多 Agent 协作做了什么？**

**A（GPT）：我的判断是，证明思路很常规，主要贡献是协作工程。** 它把证明图做成可由不同参与者接手、提交和复用的共享任务系统，具体包括：

- **固定任务规格：** 大家围绕同一张命题卡工作，里程碑统一关键目标的表述。
- **独立验收与汇合：** 各方分别提交子证明，平台检查归约关系，依赖补齐后自动确认上层结果。
- **共享成果：** 检索、复用其他人的定理，并记录署名与引用。

**方法新意有限，工程组织是重点。** 这些设计把已有的分解证明思路做成了一条可用的开放协作流程；长期价值取决于实际能降低多少接手、复用和维护成本。[论文 §3–4](https://arxiv.org/html/2608.28433v2#S3)

## Q3：复现难在哪

**Q：** 上面你提到说“工程组织”是重点，请问这个工程组织有任何难处吗，就是提供一个api、然后后台存储一下可以公开复用的subagent、维护一下证明地图，看起来似乎扔给codex来做很快就能重新手搓一个prove2me复现出来，是这样吗？既然设计上没太大新意，那工程上的难处是啥？

**A（GPT）：核心原型容易复现，Codex 可以承担大量实现；“几分钟完整复现”低估了验证和集成测试的工作量。** 这里存储、复用的是**定理与证明**，subagent 是执行者。具体工程量主要在：

- **固定声明、分离证明：** 子命题的目标保持不变，各方独立提交证明，减少共享文件修改和合并冲突。
- **可信验收：** 核对目标类型，拒绝证明中的 `sorry` 与额外公理，追踪导入依赖，并固定 Lean／Mathlib 环境。
- **正确汇合：** 一个归约的子命题全部完成后，自动向上确认结果；多条证明路线和异步提交也要保持状态一致。[论文 §3–4](https://arxiv.org/html/2608.28433v2#S3) · [验证规范](https://github.com/prove2me/prove2me_workspace/blob/main/references/prove.md#reductions-decompose-core-proofs)

**我的评价：这些属于成熟工程问题，技术壁垒有限。** Prove2Me 的价值集中在把流程做成可用的公共平台、积累可复用成果；此前“工程组织是重点”指贡献所在，并不代表工程技术很难复现。

## Q4：还有哪些方案

**Q：其他类似平台怎么做？Prove2Me 是规模最大的吗？有没有更大或做得更好的？**

**A（GPT）：最接近其开放协作定位的可看 Tau Ceti；最接近“共享证明图＋多 Agent 自动推进”的可看 LeanMarathon。** 各条路线的重点如下：

| 方案 | 怎么做 | 适合关注什么 |
|---|---|---|
| [Tau Ceti](https://github.com/TauCetiProject/TauCeti) | 人制定路线与审查规范，AI 写 Lean、提交 PR，通过 CI 与审查集成 | 多人、AI 共建可复用数学库 |
| [LeanMarathon](https://arxiv.org/abs/2606.05400) | 构建、审核、证明、修复 Agent 围绕共享 blueprint 分工 | 长程自动形式化与并行任务组织 |
| [GitHub＋Lean blueprint](https://github.com/PatrickMassot/leanblueprint/blob/master/README.md) | 用数学蓝图标注依赖与进度，通过 PR、CI 合作 | 项目路线图和人工组织协作 |
| [Mathlib](https://github.com/leanprover-community/mathlib4) | 社区审查、维护基础数学定义与定理 | 通用数学库的质量、API 与长期维护 |
| [Lean Pool](https://github.com/LeanPool/lean-pool) | 用 CI、lint 与 LLM 审查归档已完成项目并维护版本 | 形式化成果的保存与检索 |
| [Formal Conjectures](https://github.com/google-deepmind/formal-conjectures) | 汇集猜想的 Lean 声明、来源与结果 | 找题目、明确规格、构建评测资源 |

**目前没有依据把 Prove2Me 称为规模最大。** 本次查阅的 [Lean Pool README](https://raw.githubusercontent.com/LeanPool/lean-pool/main/README.md)报告 **308 个项目、约 1172 万行 Lean**；Prove2Me 论文最大单个案例为 **15.1 万行**。前者是全库归档量，后者是单项目体量，比较时需要统一口径。[Prove2Me 表 1](https://arxiv.org/html/2608.28433v2#S5)
